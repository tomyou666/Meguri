# エクスポートプレビューの仮想スクロール

選択ノードが多い、または 1 ノードの本文が巨大だと、プレビュー開始で DOM が重くて操作できなくなる問題の調査と対策。実装前の設計メモ。採用案は **TanStack Virtual（`@tanstack/react-virtual`）で行を描画し、本文は画面の前後だけ持つ**。行は Go がブロック境界で切った断片で、TypeScript はそれをノード区間と同じ型として扱う。

## 結論（採用）

- 仮想リストの `count` は行数。index は、チェックや並べ替えを変えるまで安定
- 1 行の型は共通。行 id / ノード id / `url` / 本文。見出しと区切りはフラグではなく、設定と先頭行から描く。対象は markdown プレビュー、markdown ソース、HTML。左の順序ツリーは対象外
- 小さいノードは 1 行。巨大ノードは Go が複数行に分ける。チェック、保存、左ツリーが扱う単位はグラフのノードのまま
- 見出しは、そのノードの先頭行だけに付ける。区切りは 2 件目以降のノードの先頭行の前だけ。別の仮想行にはしない
- 開始時に全行のバイト長と、先頭行かどうかだけ受け取る。本文は含まない
- 本文は、見えている範囲と overscan の前後 1 画面だけ持つ。採用は行 id と世代が一致した応答だけ。範囲外の本文は捨てる。`count` は縮めない
- 未計測の高さは `max(64, 240 × バイト長 / 8192)`。先頭行は +48px。測った高さは、形式や表示設定を変えるまで残す
- 取得は新規のスリム API。既存 `GetNodeResults` は使わない
- 仮想化は件数で切り替えない。常時この経路
- 保存はプレビューのメモリを使わない。Go がファイルへ追記する。コピーボタンは消す

「本文配列の先頭を消して `scrollTop` を手で引く」は採らない。消すと index がずれ、`scrollToIndex` と安定キーが効かなくなる。捨てるのは画面外の本文だけで、行番号はそのまま残す。

## 現状

`ExportApp.runPreview` がチェック済み ID をまとめて `GetNodeResults` し、`buildExportPreview` / `buildExportPreviewSections` で全件を state に載せる。

`ExportPreviewPane` は `ScrollArea` の中で次を全部マウントする。

| 表示 | 今の DOM |
| --- | --- |
| markdown プレビュー | セクションごとに `ReactMarkdown` |
| markdown ソース | 結合済み文字列の `<pre>` 1 本 |
| HTML | セクションごとに `dangerouslySetInnerHTML` |

`GetNodeResults` の `CrawlResultDTO` は `markdown` に加え `html` / `rawHtml` / `jsonBody` / `links` も返す。プレビューが markdown だけのときも、不要な本文が IPC に乗る。

保存とコピーは、プレビューが作った結合文字列（分割 ZIP のときは全ファイル配列）を前提にする。保存ボタンはプレビュー済みでないと押せない。

想定規模は数百〜数千ノード。ノード単位の仮想化だけだと、画面に入った 1 セクションが巨大なときに DOM が残る。

## 採用設計

### 仮想化の単位

`useVirtualizer` の `count` は行数。`getItemKey` は行 id（グラフのノード id だけにしない。同じノードの 2 行目と衝突する）。

各行の描画コンポーネントは 1 つ。Go が分けた行も、ノード 1 件の行も同じ型で描く。

| 表示 | 行の中身 |
| --- | --- |
| markdown プレビュー | 先頭行なら見出し、2 件目以降のノードならその前に区切り + `ReactMarkdown` |
| markdown ソース | 同じ位置に見出しと区切り + その断片の `<pre>`。結合 `<pre>` はやめる |
| HTML | 同じ位置に見出しと区切り + その断片の HTML |

見出しと区切りの文字列は、保存と同じ規則でフロントが描く。ファイル用の結合文字列は作らない。行 id からグラフのノードが分かるようにする。ラベルはフラットツリーの `label` か `urlNormalized`。`url` はプレビュー内リンクの基準 URL に使う。

含まれるノードの並びで最初のノードには区切りを付けない。2 件目以降は、そのノードの先頭行の前に区切りを置く。見出しは `includeHeading` のときだけ、各ノードの先頭行に `## ${text}` を置く（`text` は見出しフィールド。現行どおりエスケープしない）。

ソースとプレビューは同じ markdown 断片の描き分け。切り替えでは取り直さない。測った高さだけ捨てて、見えている行から測り直す。バイト長はそのまま使う。

スクロール親はプレビュー面だけの native `overflow: auto` にする。Radix `ScrollArea` の viewport は使わない。仮想化が測る要素と、ユーザがスクロールする要素を分けると位置がずれる。

### Go の分割

プレビュー表示のときだけ割る。保存のファイルには、割る前の本文を書く。

目標は約 8KB（8192 バイト）。境界はブロックの間だけ。

| 形式 | 切り方 |
| --- | --- |
| markdown | goldmark のブロック（見出し、段落、リスト、表、コードブロックなど）を、8KB に収まる範囲でまとめる |
| HTML | `html` / `body` / `div` / `section` / `article` / `main` を潜り、その子の間で 8KB にまとめる |

断片は元バイト列のスライスである。goldmark や HTML パーサで描き直さない。markdown の境界は goldmark のソース位置で決める。goldmark は直接依存にする。

表、リスト、`pre` の途中では割らない。1 ブロックが 8KB を超えたら、そのブロックだけで 1 行にする。これが残リスクである。HTML を兄弟の間で割ると、親の flex や grid はプレビューでは再現しない。保存ファイルは割る前の本文なので、この差はプレビューだけである。脚注定義や参照リンクが別の行にあっても、定義を各行へ複製しない。プレビュー上は解決しないままにする。

本文が空のノードは行を作らない。結果が無いノードは行を作らない。件数は行メタの `skippedCount` で返す。結果はノード id で対応づける。現行の URL 引きは使わない。同じ URL のノードは、それぞれ自分の結果を使う。

Go がセッション中に持つのは、分割済み文字列の全配列ではない。行 id、ノード id、バイト長、先頭行か、元本文内の開始位置と長さである。本文 API はその範囲を元本文から切って返す。スクロールのたびに先頭から解析し直さない。

キャッシュのキーは `workspaceId`、順序どおりのノード id、`format`、世代である。形式を変えたら捨てて作り直す。チェックや並べ替えを変えたときも作り直す。`export:open` でも捨てる。

### データウィンドウ

開始時の応答は、全行のバイト長と、その行がノードの先頭かどうか。本文は含まない。

本文として持つのは、仮想リストが見ている index に overscan を足した範囲の、前後 1 画面である。overscan の行も本文を持たないと、マウント済みの行が空になる。高さの見積もりと実測から、その index 範囲を決める。範囲外の本文は Map から削除する。仮想リストの `count` は縮めない。

未取得の index は、バイト長から見積もった高さの骨格を置く。本文が届いたら実 DOM を測り、高さ配列を更新する。

取得は、見えている範囲が今持っている本文の窓から外れたときだけ。窓の端に触れただけでは取らない。

本文応答は、返ってきた各行の id が、その index の行メタの id と一致するときだけ Map に入れる。一致しない応答は捨てる。要求した範囲と違う応答も捨てる。チェック、並べ替え、形式変更、`export:open` は世代を進める。世代が違う応答は捨てる。

プレビュー開始時は index 0。最初に取るのは、先頭から 1 画面分とその下 1 画面分（overscan を含む）。行メタが返るまで `count` は 0 である。待ち表示はメタの戻りを待たずに出す。メタのために全ノードを一度解析するので、開始の待ちは残る。

クライアントが全行分として持つのは、バイト長、先頭行フラグ、測った高さ、行の総数である。本文の全件は持たない。

### 高さキャッシュとスクロール補正

`estimateSize(index)` は、測り済みならその高さ。未計測なら次の式。

```
max(64, 240 × バイト長 / 8192)
```

先頭行はさらに +48px。本文を捨てても、測った高さは残す。再訪時は推定に戻さない。

残るジャンプは「見積もりと実測の差」で、上にある行の高さが変わったときである。TanStack Virtual は、ビューポートより上のサイズ変化で scroll 位置を補正する。

- 初回計測の補正は、スクロール方向に関係なくかかる
- 再計測の補正は、既定では上方向スクロール中スキップされる（上へ辿っているときの連鎖ジャンプを避けるため）
- `shouldAdjustScrollPositionOnItemSizeChange` はオプションオブジェクトでは読まれない。仮想izer インスタンスへ代入する
- 設定変更で高さを全破棄したあとは、維持したい行へ `scrollToIndex` する

次の操作では、測った高さを全破棄して測り直す。

- format（markdown / HTML）
- 見出しの有無・見出しフィールド
- 区切り文字
- ソース ↔ プレビュー

format の変更では、バイト長と先頭行フラグから取り直す。ソース ↔ プレビューは、持っている本文の描き分けだけで、バイト長も本文も取り直さない。見出しや区切りの変更も、分割は変わらないのでバイト長は残す。

表示設定の変更では、今の行 index を維持する。チェックや並べ替えを変えたら先頭に戻し、バイト長から取り直す。

### スリム API

プレビューの取得に `GetNodeResults` は使わない。html / raw / json / links まで載る。

2 つに分ける。

| 呼び出し | 入力 | 戻り |
| --- | --- | --- |
| 行メタ | `workspaceId`、順序どおりのノード id、`format` | 行ごとのバイト長、先頭行か、行 id、ノード id。`skippedCount`。本文なし。世代 |
| 本文 | `workspaceId`、行の index 範囲、`format`、世代 | その範囲の行 id、ノード id、`url`、本文。見出しを出すかは返さない |

先頭行フラグは行メタだけが持つ。本文側は行 id の一致で採用を判断する。見出しと区切りは、フラットツリーとエクスポート設定からフロントが描く。

保存はこの API をループしない。下の Go 書き出しに任せる。

### 保存

プレビューの本文 Map とは独立。プレビューしていなくても、チェック済みノードだけで保存できる。プレビュー API はループしない。

手順は次のとおり。

1. 保存ダイアログで確定パスを決める。ここではまだ本文を読まない
2. Go が一時ファイルへ追記する。単一ファイルも ZIP も Go が書く。書く本文は分割前のノード全文
3. 完了したら確定パスへ移す

進捗は完了ノード数 / 全体。Wails イベントでエクスポート画面を覆うオーバーレイに出す。中止ボタンを置く。保存中はプレビュー操作を止める。

中止は保存専用のキャンセル API で context を止める。一時ファイルは削除する。確定ファイルは残さない。ダイアログを閉じただけの中断は、追記を始めない。

連結規則は現行の `exportTree.ts` と同じにする。プレビューの描画もこの規則に合わせ、ファイル用の結合はフロントで作らない。

- 本文は markdown なら `markdown`、HTML なら `html`。空ならそのノードは書かない
- 結果はノード id で取る
- `includeHeading` のとき、本文の前に `## ${text}\n\n` を付ける。`text` は見出しフィールドが `label` ならラベル、そうでなければ正規化 URL。見出し自体はエスケープしない
- ノードの間だけ区切りを挟む。先頭ノードの前には置かない
- 区切りは `\r\n` / `\n` / `\r` / `\t` / `\\` を解釈してから使う。HTML のときだけ `& < > " '` をエスケープする
- ZIP の基の名前は、見出しフィールドが `label` ならラベル。そうでなければ URL のパス末尾（末尾スラッシュは除く）。パスが空ならホスト名。URL として解釈できなければ正規化 URL のまま
- ファイル名は `[\/:*?"<>|]` を `_` にし、連続空白を 1 つに畳み、前後を削り、120 文字で切る。空なら `export`
- 同じ基の名前は、1 件目が `stem.ext`、2 件目以降が `stem-2.ext`、`stem-3.ext` の順（`stem-1` は使わない）

コピーボタンはエクスポート画面から削除する。

## 代替案（お勧め順）

採用が上の設計。下がるほど「今回はやらない」。

### 2. ノード 10 件を 1 ページにし、現在ページ ±5 の本文を持つ

DOM も本文メモリも、小さいノードが並ぶときは足りる。1 ノードが 8KB を大きく超えると、その 1 行が画面いっぱいに残る。行分割に置き換えた理由はこれ。

### 3. 描画だけ仮想化し、本文は開始時に全件持つ

DOM は軽くなる。IPC と JS ヒープは今のまま。数千ノード、または巨大な 1 件では本文が先に重い。

### 4. 仮想リスト自体を画面分の配列にし、先頭削除で `scrollTop` を引く

本文だけでなく index 列も縮む。`scrollToIndex` の意味が「全体の何件目」ではなくなる。画面外の本文だけ捨てれば、同じメモリ上限になる。

### 5. クライアントがノードごとの段落数だけを目録として持つ

行メタ（バイト長と先頭行フラグ）を全行分先に受け取るので、別の目録は要らない。総数と見積もりはそこから計算する。

### 6. 固定高さ

計測も補正も要らない。本文の長さ差で余白か見切れが出る。バイト長比例の見積もりと実測に劣る。

### 7. 件数閾値未満は今の全件 DOM

小さいときだけ別経路になる。常時仮想化するオーバーヘッドの方が小さい。二重実装にしない。

### 8. 既存 `GetNodeResults` の ID スライス

ページングはできる。1 件でも html / raw / json が付く。表示中の形式の断片だけ返す API にする。

### 9. TypeScript で ReactMarkdown や HTML を再分割する。ノード行の中に内側スクロールを作る

レイアウトが文書全体に依存する。エクスポートは 1 本のスクロールである。分割は Go の AST に寄せ、描画側は返ってきた行をそのまま仮想化する。

### 10. 保存もフロントが全文結合

プレビューと分離しても、保存のピークメモリが全本文 + 結合文字列になる。Go の追記にしない理由がない。

### 11. HTML プレビューは対象外

行の型は markdown と同じである。形式切り替えで HTML の行メタと本文を取り直す。対象外にすると、多ノードの HTML だけ今の重さが残る。

## 確定判断

1. 調査メモは本ファイル。実装手順の詳細ではなく、採用と棄却を残す
2. 仮想行は共通の型。markdown プレビュー、markdown ソース、HTML。左ツリーは対象外。チェックと保存はグラフのノード
3. Go が約 8KB、ブロック境界で行に分ける。断片は元バイト列のスライス。表・リスト・`pre` の途中では割らない。HTML は `html` / `body` / `div` / `section` / `article` / `main` を潜る。超えた 1 ブロックは 1 行のまま。参照定義の行またぎは直さない
4. 見出しはノードの先頭行だけ。区切りは 2 件目以降のノードの先頭行の前。`getItemKey` は行 id
5. 初手から描画仮想化と本文ウィンドウの両方。描画だけ先、は採らない
6. `count` は行数。捨てるのは画面外の本文だけ。先頭削除の手補正はしない
7. 開始時に全行のバイト長と先頭行フラグと `skippedCount`。本文は見えている範囲と overscan の前後 1 画面。常時 ON。結果はノード id で取る
8. 未計測は `max(64, 240 × バイト長 / 8192)`。先頭行は +48px。測った高さは format / 見出し / 区切り / ソース↔プレビューで破棄
9. ソース↔プレビューは再取得しない。format 変更では行メタから取り直す。見出しと区切りの変更ではバイト長を残す
10. 設定変更は同じ行 index を維持。チェックと並べ替えは先頭から取り直す
11. ジャンプ対策の本筋は、見積もりと実測の差。インスタンスのサイズ補正と `scrollToIndex`。本文は行 id がメタと一致し、世代が同じ応答だけ採用する
12. スリム API は行メタと、index 範囲の本文。既存 `GetNodeResults` はプレビューに使わない。Go が持つのはオフセットと世代。`export:open` で捨てる。スクロール親はプレビュー面の native overflow
13. 保存はダイアログのあと Go が追記する。連結規則は現行 `exportTree.ts` と同じ。書くのは分割前のノード全文。単一ファイルと ZIP。進捗オーバーレイと専用キャンセル API。中止時は一時ファイルを捨てる。コピーは削除。プレビュー済みを保存の条件にしない
14. ノード 10 件 × 前後 5 ページの本文窓は採らない。TypeScript 側の内側仮想化も採らない
